❯ why is it necessary to have the fn/fn_g_p/fn_p_g/fn_p_p type system? Can it   
  be simplified?                                                                

⏺ Short version: those four type strings do nothing at runtime — evaluation is
  dynamically-typed Python. They exist solely to prune enumeration. So the
  question is really "does the searcher need this much type structure to stay
  tractable, and is four the minimum?"

  What the types actually buy you

  The enumerator is monomorphic: every primitive has one concrete type, and
  D.bytype[tailtype] is a dict lookup that decides which primitives may fill a
  given argument slot (cenumerate, groom, makepaths in ecd.py all key off it).
  Types are the only pruning mechanism.

  Concretely, pipe_gpg's first slot is typed fn_g_p. Only dup and compose_gp
  inhabit that type, so the searcher tries ~2 things there. Collapse everything
  to a single fn type and that same slot can be filled by step, optimize,
  compose, wall_at, sync_to_world, dup, mapsnd(...), compose_gp(...) — ~9
  candidates, most of which build a grid→grid where a grid→pair is needed, so
  pipe_gpg then hands a grid to a commit expecting a pair and throws. You'd
  still get the right answers (the try/except eats the garbage), but the
  branching factor multiplies at every slot across a depth-14 tree. The four
  types aren't decoration; they're what keeps belief in reach.

  Why specifically four

  There are two objects in this little category — grid and pair — so there are
  four arrows between them: grid→grid (fn), grid→pair (fn_g_p), pair→grid
  (fn_p_g), pair→pair (fn_p_p). You use all four because you asked for dup,
  mapsnd, and the two composers to be separate, discoverable nodes. That's the
  key tradeoff:

  ▎ In a monomorphic DSL, the number of types is dual to how finely you 
  ▎ decompose. Every type you delete = one combinator you must pre-fuse = one 
  ▎ node you wanted discoverable that you've now re-hidden.

  Two real ways to simplify

  A. Cheap, but undoes the decomposition — fanout. Replace dup + mapsnd +
  compose_gp with one combinator:
  fanout(derive) :: fn -> fn_g_p      w |-> (w, derive(w))
  belief = (pipe_gpg (fanout POLICY) (sync_to_world av))
  This drops fn_p_p (and compose_gp, mapsnd) entirely — down to two function
  types, fn_g_p and fn_p_g. But it re-buries the private copy inside fanout,
  which is exactly the w.copy() you split out in the first place. So it's a
  simplification that costs you the file's whole point. Same goes for fusing
  fn_p_p away via a compose_gp_map(produce, f) — you'd lose mapsnd as a node.
  Note fn_p_p already has only one constructor (mapsnd <fn>), so it's the
  cheapest type to drop if you decide the dup/mapsnd split isn't worth
  surfacing.

  B. Principled, but a bigger change — parametric polymorphism. All four
  function types are instances of one polymorphic arrow a → b, and
  compose/compose_gp/pipe_gpg are literally the same function compose : 
  (a→b)→(b→c)→(a→c). The proliferation is purely an artifact of having no type
  variables. With Hindley–Milner-style types + unification (what DreamCoder
  actually does) you'd keep one →, one compose, and just dup : grid→pair, mapsnd
  : (grid→grid)→(pair→pair), sync : int→(pair→grid). The four strings collapse
  into the unifier's job. Cost: the enumerator is built on exact string-keyed
  bytype buckets; you'd have to replace those with unification at each step.
  That's the honest "right" simplification, but it's an enumerator rewrite, not
  a DSL tweak.

  Recommendation

  Keep the four types. They're free (just strings), they're what makes the
  depth-14 search tractable, and they're the exact shadow of the granularity you
  deliberately chose — dup and mapsnd as independent primitives. The only
  simplification that doesn't cost you something is option B, and that's worth
  doing only if you start adding more object types (triples, typed channels) and
  the monomorphic arrow-count starts exploding combinatorially. At two objects
  / four arrows, you're below that threshold.

  If you want, I can sketch the fanout variant as a file15b so you can A/B the
  search cost and see how much the dup/mapsnd split actually adds to enumeration
  time.

❯ why use types grid, pair_gg, fn_g_p, and fn_p_g when we could use grid,       
  (grid, grid), grid -> (grid grid), and (grid, grid) -> grid?                  

⏺ Because in this enumerator a type is nothing but an opaque hash key. The only
  thing the searcher ever does with a type is D.bytype[tailtype] — bucket
  primitives by exact equality of the type value (see infer, makepaths, groom,
  and isequal's n1.type == n2.type). Nothing ever parses or decomposes a type
  string.

  So the direct answer: 'fn_g_p' and the literal string 'grid -> (grid, grid)'
  are behaviorally identical. You could globally swap in the structural strings
  today and the run would be byte-for-byte the same — they're just longer,
  equally-opaque dict keys. The short names are an ergonomic, honest label for
  an atom; the structural notation would be cosmetic at best and misleading at
  worst, because it advertises structure the machinery doesn't honor (a reader
  would expect the checker to know (grid,grid)->grid is a function returning a
  grid, and it doesn't — it's one indivisible token).

  Three things make this precise:

  1. There already is structure, exactly one level deep — at the primitive 
  signature. Each Delta carries arrow = (tuple(tailtypes), type). So
  sync_to_world really is typed (int,) -> fn_p_g structurally. What's atomic is
  the slot types — the return type and each argument type. fn_g_p/fn_p_g/fn_p_p
  are precisely those slot atoms.

  2. They're atoms because the arguments are higher-order. fork takes commit :: 
  fn_p_g — the argument is itself a function value. For the flat bytype bucket
  to enumerate "things that produce a pair→grid function," that function type
  has to be a single token. fn_p_g is the reified name of the arrow
  (grid,grid)->grid so a first-class function can be a bucket key. Writing it as
  the structured (grid,grid)->grid only buys you something if argument slots
  are matched structurally rather than by equality — i.e., if the enumerator
  unifies type terms instead of hashing them.

  3. Structural notation is load-bearing only with unification. This is the same
  fork in the road as last time: ground (variable-free) structured types
  matched by structural equality are identical in power to atomic strings — you
  gain nothing until you add type variables. compose : (a->b) -> (b->c) -> 
  (a->c) is the only thing that needs to look inside -> (to unify b), and that's
  what would collapse your four arrow-atoms + three composers into one -> and
  one compose. Without polymorphism, grid -> (grid, grid) is just a verbose
  alias for fn_g_p.

  So the choice isn't "named atoms vs. structural types" — it's "atoms-as-keys
  (cheap dict lookup, current) vs. structural-types-with-unification (parses
  ->/(,), enables one polymorphic compose)." The structural spelling without the
  unifying machinery is pure notation. Given you're at two objects and four
  arrows, the atoms are the right call; the structural representation earns its
  keep only once you add a HM-style checker, which is worth it only if the
  object/arrow count starts exploding.
