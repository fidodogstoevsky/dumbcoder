  Bottom line

  The dangling fn_1 breaks nothing, in any consumer — and the code structurally
  prevents it from ever being a live unresolved reference in a registered
  abstraction. fable correctly identified a cosmetic artifact but mis-diagnosed
  it as a latent bug.

  The load-bearing fact: bodies are resolved object graphs, not lazy names

  When an abstraction is registered, its body is parsed with hiddentail = tr(D, 
  body_str) (ecd.py:499) and the result is a Delta object graph with every 
  child's hiddentail already baked in. Nothing downstream ever re-looks-up a
  child by name in D. Consequences:

  - A name missing from the final library D is at most a cosmetic repr in
  str(d); it is never consulted during evaluation or normalization.
  - A registered abstraction cannot carry an unresolved reference: registration
  requires tr(D, body_str) to succeed (ecd.py:498–504), which requires every
  token to resolve in D at that moment; a token that doesn't resolve throws →
  the abstraction is skipped (skipped_bodies[name]=…; continue) and never enters
  the library. Since fn_10 is in the library, its body parsed cleanly.

  I verified this: every one of the reconstructed bodies re-parses under D, and
  a program using the most deeply-nested abstraction (fn_4, whose body nests
  both fn_1 and fn_0) normalizes to pure primitives with zero stray fn_ tokens.

  Where fn_10's body actually gets consumed

  Run side (experiment.py), the in-memory library:
  1. save_run_artifact (experiment.py:1291–1298) serializes [d.repr for d in 
  D.invented] — names only. Bodies are never written. sols are saved as
  str(simplify(normalize(sol))) — I confirmed all 200/186 saved solutions are
  100% primitive, no fn_ tokens. So nothing dangling reaches disk.
  2. _belief_ctor_in_D (experiment.py:142) does
  str(simplify(normalize(deepcopy(d)))) — walks the object graph, resolves
  fully. This is the only run-side reader that touches bodies.
  3. Report tables (fable's log lines 72/91) print usage counts and repr names.

  Downstream (mdl_margin.py, corpus_dl.py), separate processes: they read the
  primitive sols from disk and re-stitch from scratch with a fresh D
  (n_already_invented=0), producing a self-consistent library fn_0–fn_5 whose
  nested references (fn_3→fn_1, fn_4→fn_0/fn_1, fn_5→fn_1) all resolve. I ran
  _dl and rewrite_through_library on programs that use those nested abstractions
  — all succeed. This path never sees the run's fn_10 body at all; _remap_names
  just renames the run's fn_6–fn_11 tokens in the saved rewritten strings onto
  the freshly-reconstructed names.

  On fable's specific claim

  fable's table (log lines 72/91) shows fn_10 usage counts, not its body — the
  "body literally says fn_1" came from a live session I can't see, and it isn't
  reproducible from committed code + artifacts, because:

  - saturate_stitch calls D.reset() (ecd.py:317) before re-registering, so
  round-1's fn_1 is gone from D during round-2 registration. A body string
  literally containing fn_1 would fail tr() → be skipped, not registered as
  fn_10.
  - A this-round fn_1 token is rewritten fn_1→fn_7 by the remap loop
  (ecd.py:488–491, range(6)) before parse. So it can't survive as literal fn_1
  either.

  What fable most likely saw is str(fn_10.hiddentail) printing a child node's 
  repr. In my offset-0 reconstruction str(fn_3.hiddentail) legitimately prints
  (fork (fn_1 …) …) because the child is library member fn_1. With the run's +6
  offset that child is fn_7 and prints fn_7. Either way it's a resolved,
  self-contained object — cosmetic naming, not a dangling pointer.

  The one thing genuinely worth a guard (defense-in-depth, not an active bug)

  fable's broader worry — "normalize isn't fully covering enumerated solutions
  that reuse prior-round abstractions" — is empirically false here: the saved
  sols include round-2 solutions found against a library containing fn_0–fn_5,
  and every one normalized to primitives.

  But the remap at ecd.py:488–491 does blindly rewrite any fn_i (i in
  range(n_abstractions)) in the body string. If normalize ever did leak a
  prior-round token whose index happened to fall in that range, it would be
  silently misremapped to the wrong this-round token — a semantic corruption
  with no crash. So the correctness of the final library rests entirely on
  normalize never leaking (which holds), with no assertion backstopping it. If
  you want a cheap belt-and-suspenders: assert not re.search(r'fn_\d+', str(t))
  on the trees fed to stitch at ecd.py:316 — it would turn any future normalize
  regression into a loud failure instead of a silent conflation. That's the only
  actionable item, and it's a guard, not a fix.
