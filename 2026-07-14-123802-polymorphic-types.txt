  Where you already are

  Your Delta trees are typed lambda terms already — you just have the
  monomorphic fragment:

  - The term language is there: _lam_impl + _var_sentinel give you abstraction
  and bound variables; hiddentail is a learned abstraction's body (DreamCoder's
  "invented primitive"); application is a node with tails.
  - The type language is the ground (variable-free) fragment: types are string
  tags ('fn', 'pair_gg', 'fn_g_p', 'util', 'dir'), and arrow = 
  (tuple(tailtypes), type) is a first-order arrow. No type variables, no → as a
  constructor you can nest arbitrarily — fn is an opaque atom, not grid → grid
  structurally.
  - Enumeration is type-directed but by exact-match: ecd.py:53‑55 buckets
  primitives into bytype[d.type], and a hole of type t is filled from bytype[t]
  by dictionary lookup. That dictionary lookup is precisely the thing
  polymorphism replaces with unification.

  So the gap between you and DreamCoder isn't the term representation — it's
  that your types are ground atoms matched by ==, where DreamCoder's are
  terms-with-variables matched by Hindley–Milner unification.

  What polymorphism would concretely change

  Three changes, in increasing cost:

  1. Types become terms, not strings. Instead of 'fn', a type is a small tagged
  tree:

  # base/atomic
  tgrid  = ('grid',)
  tint   = ('int',)
  # constructors
  ('→', a, b)          # was your tuple arrow (a,) , b
  ('×', a, b)          # was pair_gg, now structural: pair_gg ≡ ('×', tgrid, 
  tgrid)
  # variables
  ('var', 0)           # the new thing

  fn is now the derived type ('→', tgrid, tgrid), fn_g_p is ('→', tgrid, 
  ('×',tgrid,tgrid)), etc. Your arrow field already holds an arrow; you'd just
  let its leaves be ('var', n).

  2. Primitive types become schemes. The payoff lands here. A polymorphic
  primitive carries quantified variables that get freshly instantiated at each
  use:

  compose : ∀a b c. (b→c) → (a→b) → (a→c)
  dup     : ∀a.     a → (a × a)
  mapsnd  : ∀a b c. (b→c) → (a×b → a×c)      # bifunctor 'second'
  id      : ∀a.     a → a

  3. Hole-filling becomes unify-then-recurse. When expanding a hole of request
  type R, instead of bytype[R], you: take each primitive, instantiate its scheme
  with fresh vars, unify its result type with R; if it unifies, the
  substitution tells you the (now-refined) types of its argument holes. That's
  the whole mechanism.

  Why this matters for your project specifically

  This isn't abstract — your monomorphism is currently forcing exactly the
  duplication polymorphism exists to kill. Look at your composers:

  compose     # fn,    fn    -> fn          (dsl.py:53)
  compose_s   # sfn,   sfn   -> sfn         (dsl.py:167)
  compose_gp  # fn_g_p, fn_p_p -> fn_g_p    (dsl.py:336)
  pipe_gpg    # fn_g_p, fn_p_g -> fn        (dsl.py:342)

  These are one primitive, compose : (b→c)→(a→b)→(a→c), instantiated at four
  type assignments. Your own file15 comment admits it (dsl.py:326): "the 
  monomorphic type system has no generic compose across grid/pair arrows." Same
  with dup vs dup_g, and mapsnd/on_model — which is genuinely the polymorphic
  bifunctor second, not a grid-specific op.

  And that connects straight to synthesis-not-primitive: polymorphism is the
  principled reason dup should be the diagonal Δ : a → a×a rather than a bespoke
  dup_g. The combinators you want stitch to discover (dup, mapsnd, compose) are
  exactly the textbook product-category combinators that are born polymorphic.
  Making them so is the type-system expression of "general, non-mental parts."

  The tension you should weigh

  Polymorphism cuts both ways against your "minimize the interpreter" ethos:

  - For: fewer, more general primitives; the decomposition stops looking
  reverse-engineered because the parts are provably generic.
  - Against: you trade an O(1) dict lookup for a unifier, and every primitive
  now potentially applies at every hole (modulo unification), enlarging the
  branching factor your enumerator in ecd.py already has to budget through.
  DreamCoder pays for this with aggressive type-directed pruning; you'd be
  adding interpreter machinery, which is the thing you've been trying to shrink.
  - Orthogonal (good news): your file15 agency-signature concern — the shared av
  integer across (optimize … av) and (sync_to_world av) — is untouched. Types
  never see the value av, so polymorphism neither helps nor threatens that
  reasoning. Stitch also runs on the untyped tree, so compression is unaffected.

  Practical recommendation

  You almost certainly don't want full HM. The 80/20 is rank-1 polymorphism on 
  the combinators only — compose, dup, mapsnd, id carry schemes; everything else
  stays ground. Then unification only fires when instantiating those handful of
  primitives, and it collapses your four composers + dup_g/dup into one each.
  That gets you the generality that matters for the decomposition story without
  turning ecd.py's hole-expansion into a general type checker.

⏺ Read the enumeration core. The exact-match dispatch lives in three spots, and
  "unify-on-expand" is a surgical change to all three:

  - Deltas.infer() builds bytype: type_string → [prim_idx] (ecd.py:48‑55)
  - cenumerate() picks heads with for i in D.bytype[tp] (ecd.py:164)
  - cenumerate_fold() pops the next tailtype and recurses (ecd.py:176‑191)
  - (secondary) makepaths()/groom() mask the learned Q by bytype[tailtype]
  (ecd.py:132‑147)

  The whole idea: replace the dict lookup bytype[tp] with instantiate a head's 
  type scheme with fresh vars, unify its result against the request, and let the
  resulting substitution refine the argument requests. Here's the sketch.

  1. Type terms + a unifier (new; put near the top of ecd.py after from dsl 
  import *)

  # ── polymorphic type terms 
  ───────────────────────────────────────────────────
  class TVar:
      __slots__ = ('n',)
      _c = 0
      def __init__(self, n): self.n = n
      def __repr__(self): return f'?{self.n}'

  def fresh():
      TVar._c += 1
      return TVar(TVar._c)

  class TCon:
      __slots__ = ('name', 'args')
      def __init__(self, name, *args): self.name, self.args = name, args
      def __repr__(self):
          return self.name if not self.args else f'({self.name} {" 
  ".join(map(repr,self.args))})'

  def walk(t, s):
      while isinstance(t, TVar) and t.n in s: t = s[t.n]
      return t

  def _occurs(n, t, s):
      t = walk(t, s)
      return t.n == n if isinstance(t, TVar) else any(_occurs(n, a, s) for a in
  t.args)

  def unify(a, b, s):
      "return an EXTENDED substitution dict, or None on clash (s is not 
  mutated)"
      a, b = walk(a, s), walk(b, s)
      if isinstance(a, TVar):
          if isinstance(b, TVar) and a.n == b.n: return s
          return None if _occurs(a.n, b, s) else {**s, a.n: b}
      if isinstance(b, TVar): return unify(b, a, s)
      if a.name != b.name or len(a.args) != len(b.args): return None
      for x, y in zip(a.args, b.args):
          s = unify(x, y, s)
          if s is None: return None
      return s

  def instantiate(t, m):
      "copy a scheme, mapping each scheme-var to a fresh var (m shared across 
  result+tails)"
      if isinstance(t, TVar):
          if t.n not in m: m[t.n] = fresh()
          return m[t.n]
      return TCon(t.name, *[instantiate(a, m) for a in t.args])

  2. The type-lifting tables — this is the real design decision

  Your current atoms ('fn', 'pair_gg', 'fn_g_p'…) are opaque. Polymorphism only
  collapses your four composers if those atoms become structural arrows/products
  so unify can see fn, sfn, fn_p_p are all a→b:

  ARROW, PROD = '->', 'x'
  def _arr(a, b): return TCon(ARROW, a, b)
  def _prod(a, b): return TCon(PROD, a, b)
  G = TCon('grid')

  _STRUCT = {                                   # lift legacy string types -> 
  terms
      'fn':      _arr(G, G),
      'pair_gg': _prod(G, G),
      'fn_g_p':  _arr(G, _prod(G, G)),
      'fn_p_g':  _arr(_prod(G, G), G),
      'fn_p_p':  _arr(_prod(G, G), _prod(G, G)),
      'sfn':     _arr(_prod(G, G), _prod(G, G)),  # state == pair_gg, so sfn == 
  fn_p_p
  }
  def lift(t):                                  # everything else 
  (int/dir/util/grid) stays nullary
      return t if isinstance(t, (TVar, TCon)) else _STRUCT.get(t, TCon(t))

  # polymorphic schemes, keyed by repr — (result_term, [tail_terms]) sharing 
  scheme-var ids
  _a, _b, _c = TVar(1), TVar(2), TVar(3)
  SCHEMES = {
      'compose': (_arr(_a, _c),  [_arr(_a, _b), _arr(_b, _c)]),  # 
  compose(f,g)=g∘f
      'mapsnd':  (_arr(_prod(_a, _b), _prod(_a, _c)), [_arr(_b, _c)]),
      'dup':     (_arr(_a, _prod(_a, _a)), []),                  # terminal of 
  arrow type
      'id_fn':   (_arr(_a, _a), []),
  }

  This is exactly the "rank-1 on the combinators only" plan:
  compose/compose_s/compose_gp/pipe_gpg collapse to one compose; dup_g→dup.
  Everything else lifts to a ground term and behaves identically to today.

  Thread a substitution sub; the for i in D.bytype[tp] loop becomes filter →

  def cenumerate(D, Q, tp, budget, maxdepth, cb, sub=None, deadline=None):

      if budget[1] <= 0 or maxdepth < 0: return True
      if deadline is not None and time() > deadline: raise _EnumDone()

      req = walk(tp, sub)
      for i in D.candidates(req):
          qi = Q[i].item() if isinstance(Q[i], th.Tensor) else float(Q[i])
          if -qi > budget[1]: continue
          d = D.ds[i]

  def cenumerate_fold(D, Q, d, tailtypes, budget, offset, maxdepth, cb, sub,

  The two substantive shifts from the original:

  1. Sibling coupling. When compose's first arg fixes b (e.g. you pick an inner
  grid→pair), sub2 carries ?b ↦ pair, so the second arg's request _arr(_b,_c)
  walks to pair→?c automatically — that's why ccb threads sub2 forward to rest.
  The old code's tailtypes.pop(0) over fixed strings couldn't express this.
  2. cb gains a sub parameter. The program-complete callback (ecd.py:194) is now
  cb(d, offset, sub). The root caller passes the request as a term, e.g.
  cenumerate(D, Q, lift(root_type), …), and any cb you currently pass needs the
  extra positional (it can ignore it).

  — a superset; the real unify at expansion time does the exact pruning. Q
  itself is indexed by flat primitive id, so the recognition model is otherwise
  untouched.
