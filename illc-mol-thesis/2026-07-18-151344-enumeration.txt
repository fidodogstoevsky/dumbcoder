⏺ Where cost is computed

  The single primitive is Library.logp at ecd.py:71-79. Everything else in the
  codebase that prices a program calls it and negates the result.

  def logp(self, Q, d):
      if d.tails is None:                    # leaf: cost of picking this 
  primitive
          return Q[self.index(d)]
      out = 0
      for tail in d.tails:                   # recurse into every argument
          out += self.logp(Q, tail)
      return Q[self.index(d)] + out          # this node + subtree

  What it does: walks the program tree and sums a per-node log-probability
  Q[index(d)] for the head plus the logp of each tail. Q is the (log-softmaxed)
  grammar weight vector over the library D; index(d) locates the
  primitive/invention in the library. So logp returns the log-probability of the
  whole tree under the grammar.

  Cost / description length is then just the negative of that. The convention is
  factored out into a one-liner that's copy-pasted across the analysis scripts,
  e.g. experiment.py:797:

  def _dl(D, Q, prog):
      t = ...            # parse prog to a tree
      return float(-D.logp(Q, t))   # nats

  Identical _dl wrappers live in corpus_dl.py:67, mdl_margin.py,
  behavioral_probe.py:91, and phase3_arity.py — all commented as "same
  convention," all bottoming out in D.logp.

  Two related pieces:
  - corpus_dl._body_dl (corpus_dl.py:73) is a variant for pricing an invention's
  body: same recursion, but bound-variable holes ($i) are free since they name
  arguments rather than cost tokens.
  - makepaths/cenumerate (ecd.py:124, 155) use the same Q weights as budget
  during enumeration — that's the search-time counterpart to the post-hoc logp
  scoring.

  So: cost = -D.logp(Q, tree), and logp itself is the recursive sum at
  ecd.py:71.

⏺ How enumeration works

  The engine is a type-directed, best-first-by-description-length program 
  search. It enumerates candidate programs cheapest-first (highest probability =
  lowest -logp cost), runs each one on the task inputs, and keeps any whose
  output hits a target. There are two implementations sharing the same idea,
  selected by the budget argument in solve_enumeration.

  The default path: iterative-deepening over cost windows (cenumerate, budget ==
  0)

  The outer loop is at ecd.py:774:

  idx = 0
  while not done and time() < deadline:
      cenumerate(D, Q, _enum_type, (LOGPGAP*idx, LOGPGAP*(idx+1)), maxdepth, cb,
  deadline)
      idx += 1

  It sweeps expanding log-cost windows [0,gap), [gap,2·gap), …. Each pass emits
  only programs whose total cost -logp lands in that band, so overall programs
  come out in increasing-cost order — this is best-first / MDL-ordered search,
  done as iterative deepening so memory stays flat.

  cenumerate (ecd.py:155) expands one node:

  for i in D.bytype[tp]:                 # only symbols of the required type
      qi = Q[i]                          # this symbol's log-prob
      if -qi > budget[1]: continue       # PRUNE: head alone already too 
  expensive
      nbudget = (budget[0]+qi, budget[1]+qi)   # thread remaining budget down
      cenumerate_fold(D, Q, d, tailtypes, nbudget, qi, maxdepth-1, cb, deadline)

  Two key mechanisms:
  - Type restriction — D.bytype[tp] means each argument slot only ever considers
  symbols of the correct type. This is what keeps the search tractable.
  - Budget pruning — a symbol's own cost is subtracted from the window ceiling;
  if it already blows the budget, the whole subtree is skipped.

  cenumerate_fold (ecd.py:180) fills the argument slots one at a time:

  tailtp = tailtypes.pop(0)
  def ccb(tail, tlogp):                  # got a candidate subtree for this slot
      nd = deepcopy(d); nd.tails.append(tail)
      cenumerate_fold(D, Q, nd, rest_tailtypes, budget-tlogp, ..., cb)   # fill 
  remaining slots
  return cenumerate(D, Q, tailtp, (0, budget[1]), maxdepth, ccb, deadline)

  It recursively enumerates subtrees for the current slot (each firing ccb),
  attaches each to a copy of the node, and recurses on the remaining slots. When
  all slots are filled and the accumulated cost lies inside the window
  (ecd.py:197):

  if budget[0] <= 0 and 0 <= budget[1]:
      return cb(d, offset)               # complete program → hand to callback

  it fires cb — the callback that actually runs the finished program through the
  DSL interpreter on the task inputs (ecd.py:~745), compares the output against
  targets, and records the shortest solution per target (ecd.py:766). A time
  check raises _EnumDone to bail out of the whole recursion.

  The alternate path: single-ceiling generator (penumerate, budget > 0)

  When a positive budget is passed (ecd.py:783), it wraps the root type in an
  ephemeral node and uses penumerate (ecd.py:224) + groom (ecd.py:202) — a
  generator-style version yielding (logp, tree) pairs under one fixed ceiling
  instead of expanding windows. It relies on precomputed per-slot distributions
  from makepaths (ecd.py:124), which log-softmaxes Q within each type.
  penumerate is also used internally by the compression/saturate machinery.

  Where the probabilities come from

  Q is the grammar's flat log-prob vector. On iteration 1 it's a
  type-conditioned uniform distribution (uniform_type_q, ecd.py:854: each symbol
  costs -log(#symbols of its type)), optionally sharpened by boosting integer
  literals that literally appear in the task grid to cost-0 (content_aware_q,
  ecd.py:868). On later iterations Q comes from the learned recognition model
  Qmodel (ecd.py:878). Cheaper Q → smaller cost windows → target program found
  in an earlier pass.

  The full loop

  ECD (ecd.py:835) ties it together: dispatch all unsolved tasks to a process
  pool (_solve_one_task → solve_enumeration), collect solutions, run stitch
  compression to invent new library primitives, retrain Qmodel, and repeat — so
  each iteration the library grows and enumeration reaches programs that were
  out of budget before.

❯ what's "special casing"? what's "continuation passing"?                       

⏺ Both are jargon I reached for — here's what each means, grounded in your
  actual code, so you can decide whether to keep the words or reword.

  "Special-casing"

  Writing separate, dedicated code branches to handle particular situations,
  instead of one general rule that covers them all. "Without special-casing" =
  the code handles every case with the same uniform logic.

  In cenumerate, the point is: the enumerator does not have one branch for
  "primitive with 0 arguments" (a leaf like 3), another for "primitive with 2
  arguments" (step), another for "3 arguments," etc. It has one recursive
  procedure — cenumerate_fold (ecd.py:180) pops the next argument slot, fills
  it, and calls itself for the rest:

  if tailtypes and len(tailtypes) > 0:
      tailtp = tailtypes.pop(0)        # handle ONE slot
      ... cenumerate_fold(..., rest_tailtypes, ...)   # recurse for the rest

  A 0-arg leaf, a 2-arg step, and some future 5-arg invention all flow through
  this same code. Nobody wrote "if arity == 2 do X." That's what "arbitrary
  arity and depth are handled without special-casing" claims: the generality is
  free, falling out of the recursion.

  For the thesis you could replace it with plainer wording: "…so programs of any
  arity or nesting depth are handled by the same procedure."

  "Continuation-passing"

  A style where, instead of a function returning its result to the caller, you
  hand it a callback — "here's what to do next with each result you produce" —
  and it calls that.

  In your enumerator, cenumerate doesn't return a list of subtrees. It's given a
  callback (the parameter literally named cb) and invokes it for each subtree
  it finds. When filling step's first slot, the code builds a fresh callback ccb
  that says "take the subtree you found, attach it to a copy of step, then go
  fill the next slot" (ecd.py:184):

  def ccb(tail, tlogp):
      nd = deepcopy(d); nd.tails.append(tail)   # attach subtree to parent copy
      cenumerate_fold(..., rest_tailtypes, ...)  # "what to do next": fill 
  remaining slots
  return cenumerate(D, Q, tailtp, ..., ccb, ...) # enumerate slot, calling ccb 
  per result

  The "what to do next" — attach and continue — is the continuation. Each
  nesting level wraps the previous one's continuation, which is how partial
  trees get assembled incrementally rather than all at once.

  Caveat for the thesis: "continuation-passing" is a real term of art, and
  readers with a PL background will read it precisely — so make sure the
  surrounding prose supports it. If your audience is more cognitive-science /
  philosophy-of-mind (the belief/ToM framing suggests some are), it may read as
  unexplained CS jargon. A softer phrasing that keeps the mechanism without the
  term:

  ▎ "The tree is assembled incrementally: each enumerated subtree is attached to
  ▎ a copy of its parent node, and a callback fills the remaining argument 
  ▎ slots by the same recursion."

  That drops "continuation-passing" and "special-casing" both, at the cost of a
  little precision. Your call which register the chapter is pitched at — want me
  to swap in the plainer version, or keep the terms?
